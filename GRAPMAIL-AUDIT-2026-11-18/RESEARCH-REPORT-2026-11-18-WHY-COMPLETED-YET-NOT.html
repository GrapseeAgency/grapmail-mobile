Why GrapMail Is "Completed Yet Not" — and What the Last 10% Actually Is

Deep research report · 2026-11-18 · GrapMail (Grapsee) — native iOS/Android + web + backend

Method. Two evidence streams, both captured on or before 2026-11-18: (1) repository-level evidence from four deepening rounds on this project (Round 0 audit and fixpack; Rounds 1–3 applied this session, each verified against the live source trees), and (2) external research — feature benchmarks, UX studies, reliability engineering, deliverability rules, and software-cost research — with every source listed in §7. Claims about GrapMail are traceable to a file, a verification log, or a delivered note in grapmail-audit-2026-11-18/; external claims are sourced by number.

1. Executive summary

GrapMail did not look "completed yet not" because big features are missing. It looked that way because of six recurring seams — the boundaries that every mail feature crosses: screens → API client → backend service → mail infrastructure, and repository → production.

  1. The seam tax. One feature = four systems × two platforms. Each file can be "done" while the feature is not. Round 3 is the perfect specimen (below).
  2. Trust-boundary drift. The client trusted itself (a local humanVerified flag) while the backend demands a server-issued, single-use verification id. A gate the client can flip is not a gate. Fixed across Rounds 1–3.
  3. Payload truncation. All three platforms agreed on the shape of the register call — and all three dropped the one field the gate consumes. Signature parity is not data parity.
  4. Deploy lag. A whole list of features is implemented in the repository but not live in production (search, scheduled send, snooze, OTP, push, HTML, and more). "Done" in git and "done" for users are different states — and only the second one is visible in the app.
  5. Preference depth. Six "missing settings" turned out to be one missing backend field each — not UI work. The UI can only ask per-message until the fields exist, which reads as incomplete.
  6. Verification asymmetry. The project guards each side (honesty scripts, parity scripts) but nothing owned the seams themselves — which is precisely why Round 3's defect was invisible to per-file review, to parity tooling, and even to the kit's own patch notes.

The rest of this report: what was fixed this session as proof (§2), the competitor comparison (§3), the three questions that started the audit answered with current status (§4), why the "one by one" strategy is the correct one (§5), and the prioritized path to close the last 10% (§6).

3.2 What this table says

  • Core mail mechanics: GrapMail's repository already covers what the market treats as table-stakes — labels, threads, search operators, scheduled send, snooze folder, scheduled-worker promotion. The gap is not concept; it is deploy and preference depth (patterns 4 and 5).
  • The productivity layer: Gmail/Outlook have shipped AI copilots as defaults — Gemini summaries and Help Me Write [E1], Copilot "Coach" tone/clarity flags, and thread summarization rolling out on by default [E2][E3]. Superhuman and Shortwave sell speed + AI as the product [E5][E6]. GrapMail has none of this yet; that is a roadmap decision, not a defect.
  • The privacy lane: Proton + Fastmail show two viable strategies — full E2EE with post-quantum keys now rolling out [E20][E21], or "no ads, no tracking, no AI scanning" with standards-based sync (JMAP) and masked aliases [E15][E16][E17]. Fastmail's lesson for GrapMail is concrete: server-side features beat client-side ones — "Unlike many client-side solutions, our Snooze happens on the server… the message always comes back at your nominated time" [E14]. That is exactly the pattern GrapMail's snooze worker already follows — once deployed.
  • Reliability is a feature users judge — and it is where real apps bleed: the Android 16 notification-architecture bug that muted subsequent mail notifications [E23], IMAP folder mapping drift across devices [E25], and sync misconfigurations that hide bounces and complaints [E24]. These are the classes GrapMail's push/notification and deploy-gate work must clear.

4. The three questions that started this audit — answered, with live status

4.1 "Why is the app slow / lagging?"

Debug-build factors dominate: Jetpack Compose debug builds run interpreted with Live Literals and no R8 shrinking — commonly measured at 2–4× slower frame/startup times — while release builds with R8 + Baseline Profiles show roughly 75% startup and 60% frame-render improvements in Google's own guidance and community benchmarks [E33]. Status: explanation delivered; actionable path is release-profiling + committed Baseline Profiles, already on the fix queue. No code change was required to explain it — measurement on a release build is the next step on the founder side.

4.2 "Why has interactive preview mail not been completed?"

Two independent causes, both closed in R0: (a) the Compose screens had no image loader at all (no Coil dependency), so attachments could not render thumbnails; (b) the Files screen's backend endpoint did not exist (no /grapmail/files route; auth-service did not mount it). Both were fixed and verified (Round 0 row in §2). Nothing about "interactive preview" was blocked by a hard technical problem — it was two seams left unfinished.

4.3 "What is lacking or not yet added on iOS and Android?"

Current status board:

  • Fixed this session (R1–R3): real human verification (no skip, server-verified), the register payload, and the verify-before-register order — these were the tiny-but-fatal mobile issues: a signup funnel that a live backend would 403 twice over.
  • Implemented in repo, pending deploy (deploy gate): search operators, scheduled send worker, snooze, OTP flows, envelope views, push, HTML handling, vacation responder. "Completed yet not" in one line.
  • Build-out queue (each item = real work, mostly one backend field or one module): settings depth (§6.4 — six fields unlock ~15 settings items), offline outbox, draft autosave, custom snooze times, multi-account polish (row per §3.1), AI-assist layer if desired.

5. Why "fix them one by one" is the right strategy

The 90-90 rule — attributed to Tom Cargill (Bell Labs), popularized by Jon Bentley's "Programming Pearls" column (CACM, September 1985, originally "Rule of Credibility") — says: "The first 90 percent of the code accounts for the first 90 percent of the development time. The remaining 10 percent of the code accounts for the other 90 percent of the development time." [E29][E30] Integration-time discoveries are exactly where that second 90% hides: modules that all pass their own checks and still do not talk to each other correctly [E30]. The economics are brutal and well-measured — NIST's 2002 study put inadequate software testing at $59.5B/year for the US economy, with over half of all errors found only downstream, and its cited cost example multiplies a requirements-phase fix by 10× at integration testing and 30× after release [E31]; and finishing 90% of the features is commonly only half the effort that remains [E32].

That is why this project proceeds in rounds — one seam class per round, applied, verified, delivered:

Round Seam class Status
R0 Screens↔backend (preview/files) ✅ applied
R1 Client↔server trust (verification screens) ✅ applied
R2 Request payload (verification id) ✅ applied
R3 Flow order (verify before register) ✅ applied

6. Closing the last 10% — prioritized

  1. Ship the deploy gate. Backend + web first (verify-human endpoint, register gate, checkpoint page), then mobile builds carrying R1–R3. Everything GrapMail is "already done" only becomes visible to users through this step.
  2. Add seam contract checks — the missing guard that would have caught Round 3: a tiny script or test asserting (a) createAccount carries humanVerificationId, (b) the wizard cannot reach Create Account without a server verdict, (c) the gate consumes exactly once. This is cheap and permanently kills pattern 6 for the verification flow.
  3. Expired-verification affordance. If the id expires between challenge and Create Account (10-minute TTL), map human-verification-required on the Terms step to an explicit "verification expired — re-verify" action instead of the raw message. (Recorded as R3 follow-up.)
  4. Backend settings fields (six) — the unlock for the whole settings backlog: from-picker (/send from field), undo window, swipe-action mapping, default reply mode, remote-image policy, link-preview/HTML sanitizer choice. Each is one field + one endpoint; together they turn ~15 "documented exclusions" into working preferences.
  5. Offline outbox + draft autosave. The market's offline leader is Thunderbird (full local archives) and mid-pack apps support read+compose offline [E7][E9][E10]; Outbox pattern + WorkManager is the standard architecture. GrapMail currently has none — this is the largest remaining functional gap.
  6. Deliverability runway (service-side, before any marketing volume): SPF+DKIM+DMARC alignment, one-click unsubscribe for bulk, Postmaster Tools monitoring, complaint rate <0.1–0.3%, DMARC progression none→quarantine [E26][E27][E28].
  7. Notification reliability audit — specifically the Android 16-class muting bug [E23] and channel/priority handling, since mail notifications are the product's heartbeat.
